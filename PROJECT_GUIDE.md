## 1. Про проєкт

- **Назва:** CashFlix
- **Що робить (2–3 речення):** Сімейний бюджет для кількох людей в одному «господарстві». Облік витрат, доходів і переказів між рахунками в кількох валютах (курс НБУ), ліміти на категорії (спільні й особисті), регулярні платежі, цілі накопичень, підказки де зекономити та експорт в Excel. Оплати Apple Pay потрапляють автоматично через iOS-шорткат.
- **Для кого:** для себе й Олічки щодня (здебільшого з телефона), а також як проєкт для портфоліо на фрілансі. Закладено можливість поширити сайт іншим сім'ям.
- **Репозиторій:** github.com/GreedyClark/cashflix
- **Поточна фаза:** 1 — моделі даних.
- **Що вже зроблено:** клікабельний прототип інтерфейсу (стиль Linear на Tabler), погоджено стек, модель даних і фази. Фаза 0 (каркас, теми, меню, тести). Власна модель `User` з входом за email.
- **Що НЕ робимо зараз:** деплой, iOS-шорткат і AI-асистента — це останні фази. Старий дашборд (Supabase + Vercel) і шорткат працюють як є, поки не перенесемо дані.

### Ключові рішення

- **Господарство (Household)** — головна одиниця. Користувач створює господарство й запрошує інших за посиланням. Усі дані (рахунки, категорії, операції, ліміти, цілі, регулярні платежі) належать господарству, а не користувачу. Чужі господарства ніколи не видно.
- **Вхід:** email + пароль і «Увійти з Google» через `django-allauth`.
- **Операція — одна модель `Transaction`** з полем `type`: `expense` / `income` / `transfer`. Переказ має `account` і `to_account` і не рахується ні в витрати, ні в дохід.
- **Хто платив:** конкретний учасник або «Спільне» (поле `member` може бути порожнім).
- **Валюти:** у господарства є основна валюта (UAH). Операція зберігає `amount`, `currency`, `rate` (курс НБУ на дату операції) і `amount_base` (сума в основній валюті). Курс зберігається разом з операцією, щоб старі підсумки не змінювалися.
- **Гроші — тільки `Decimal`** (`DecimalField(max_digits=14, decimal_places=2)`), ніколи `float`.
- **Категорії** — окремий довідник у кожного господарства (назва, колір, іконка Tabler). При створенні господарства додається стандартний набір.
- **Ліміти:** на категорію на місяць. Тип — спільний (рахує витрати всіх) або особистий (тільки одного учасника). На одну категорію можна мати і спільний, і особисті.
- **Регулярні платежі** створюються командою `manage.py run_recurring`, яку хостинг запускає раз на день. Без Celery.
- **Підказки** (фаза 5) рахуються в Django правилами, без ШІ.
- **AI-асистент** (фаза 8) — тільки за бажанням, на власному ключі Gemini користувача. Ключ зберігається зашифрованим. У Gemini йдуть лише підсумки за категоріями (без назв магазинів, імен і рахунків). Цифри рахує Django, Gemini тільки формулює відповідь. Текст попередження — у DESIGN.md.
- **Мова:** українська, усі тексти інтерфейсу через `gettext`, щоб пізніше додати англійську.

## 2. Як зі мною працювати

- Я початківець у Python/Django. Пояснюй коротко, *чому* саме так, але без лекцій.
- Працюю на Windows, у терміналі PyCharm (PowerShell). Команди давай для PowerShell.
- Видавай код **по одному файлу**, окремими блоками, з повним шляхом над блоком (`apps/money/views.py`).
- Якщо змінюєш існуючий файл — давай файл повністю, а не шматок «додай сюди».
- Перед великою зміною — спочатку план у 3–5 пунктів, потім код.
- Якщо щось неясно — запитай, а не вигадуй.
- Не додавай бібліотеки, яких немає в розділі «Стек», без моєї згоди.

## 3. Стиль коду

- Мінімум коментарів: тільки там, де логіка неочевидна.
- Без докстрінгів, що переказують назву функції.
- Без «Крок 1 / Крок 2», без емодзі в коді та коментарях.
- Код має виглядати як написаний звичайним розробником.
- PEP 8, змістовні назви англійською, f-рядки.
- Секрети (ключі API, SECRET_KEY, ключ шифрування) — тільки через `.env`, ніколи в коді.

## 4. Стек

| Що | Чим |
|---|---|
| Бекенд | Django 5.2 LTS, Python 3.12+ |
| Шаблони | Django templates + **django-cotton** (компоненти) |
| Стилі | **Tabler** (Bootstrap 5) + власна тема `static/css/cashflix.css` за токенами з DESIGN.md |
| Іконки | **Tabler Icons** (SVG) |
| Графіки | **ApexCharts** |
| Інтерактив | **HTMX** (без SPA і без React) |
| Вхід | **django-allauth** (email + Google) |
| Excel | **openpyxl** |
| БД | SQLite локально, PostgreSQL на проді |
| Тести | **pytest-django**, для браузерних — **pytest-playwright** |
| Конфіг | **django-environ** |
| Пізніше (фаза 8) | `google-genai`, шифрування ключа — узгодимо бібліотеку перед фазою |

### Правила для стеку

- Компоненти, що повторюються (панель, KPI-картка, кнопка, модалка, рядок операції, рядок ліміту, поле форми), — це cotton-компоненти в `templates/cotton/`, а не копіпаст і не `{% include %}`.
- Сітка й базові компоненти — класи Tabler (`row`, `col-*`, `btn`, `form-control`…). Вигляд CashFlix — у `cashflix.css` через CSS-змінні з DESIGN.md. Кольори в шаблонах не хардкодимо.
- Ніякого інлайн-CSS і `<style>` у шаблонах. Виняток — динамічна ширина смужки прогресу через `style="width: …%"`.
- Tabler, ApexCharts і HTMX лежать у `static/vendor/` (без CDN), щоб не залежати від чужих серверів.
- Налаштування графіків ApexCharts — в одному файлі `static/js/charts.js`, дані передаються через `json_script`.
- HTMX-відповіді — окремі partial-шаблони з підкресленням (`_transaction_list.html`).
- Форми — через `ModelForm`, валідація в `clean_*`, не в view.
- Запити до БД — без N+1: `select_related` / `prefetch_related`. Підсумки рахуємо агрегаціями в БД (`Sum`, `annotate`), а не циклами в Python.
- Кожен queryset фільтрується за господарством поточного користувача. Доступ до чужих даних — 404.
- Гроші: `Decimal`, форматування сум — один шаблонний фільтр `money`.

## 5. Дизайн

### Дизайн-система

Стиль описано у **DESIGN.md** у корені репозиторію (адаптація Linear з колекції github.com/VoltAgent/awesome-design-md). Кольори, шрифти, радіуси, відступи, компоненти й правила графіків беруться звідти. Еталон вигляду — клікабельний прототип.

### Правила «щоб не виглядало як ШІ-шаблон»

- **Ніяких** фіолетово-синіх градієнтів, «Empowering Your Success», картинок-заглушок і трьох однакових карток «фіч» у ряд.
- Один акцентний колір (лавандовий), решта — нейтральні. Акцент тільки для головних дій.
- Не більше 2 шрифтів. Чітка ієрархія: заголовок, підзаголовок, текст — помітно різні за розміром і вагою.
- Відступи за однією шкалою (4 / 8 / 12 / 16 / 24 / 32 / 48 px), не «на око».
- Багато повітря: краще менше елементів на екрані, ніж тісно. Деталі ховаємо за кліком (як у лімітах).
- Тексти інтерфейсу — конкретні, про цей продукт («Додати операцію», «2 150 ₴ лишилось»), а не маркетингова вода.
- Анімації — тільки короткі (150–250 мс) і по ділу: hover, поява модалки, оновлення списку, промальовування графіка.
- Мобільна версія обовʼязкова: спочатку перевіряй на ширині 375 px.
- Порожні стани, помилки й завантаження теж мають дизайн («Операцій ще немає — додайте першу»).
- Контраст тексту — достатній для читання (WCAG AA). Обидві теми — світла й темна.

## 7. Тести

- Кожна нова фіча — хоча б один тест.
- Моделі й логіка (підсумки, ліміти, курси, підказки) — звичайні pytest-django тести.
- Обов'язковий тест на ізоляцію: користувач іншого господарства не бачить і не змінює чужі дані.
- Головні сценарії користувача (додати операцію, переказ, створити ліміт) — Playwright-тест через фікстури `live_server` і `page`.
- Перед тим як сказати «готово», перевір, що тести проходять.
